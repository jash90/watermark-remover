**Recommended order: 0 → A → C → B → (D).**
- **C before B:** C builds the ONNX infrastructure (runtime, target gating, verified model downloads, progress and cancel). If B's gate fails, D, the fix for the visible fill patch, reuses all of it.
- **B stays a spike:** a prototype on 2026-09-23 showed that interiors recover very well but edges don't yet. Its plan records the numbers and the go/no-go criteria.

## Step 0 — Land `feat/local-removal-pipeline`

Recommendation: **open a PR, then merge.** Don't push straight to `main`.

The branch has 17 commits (including these plans). They replace the whole processing path, remove Gemini, and change output files: size, palette, ICC. A PR gives a reviewable record and a revert point. All local gates are green: 35 Rust tests, clippy `-D warnings`, `npm run build`.

1. `git push -u origin feat/local-removal-pipeline`
2. `gh pr create --base main --title "Local watermark removal pipeline (no AI), output-size fixes" --body-file <summary>`. The summary covers what changed, the size table, the known issues, and a link to this roadmap.
3. Manual smoke test in the app (the only step not yet verified): open, select, remove, save, on one JPEG, one palette PNG and one transparent PNG.
4. Merge with a merge commit (not squash). The history per task is the review trail.
5. Delete the branch.

## Plan A — Hardening (spec)

1. 16-bit and greyscale inputs keep their colour type and bit depth; untouched pixels stay byte-identical.
2. Fully transparent pixels are never used as fill sources.
3. `get_image_info` reads dimensions from the header only.
4. Region arithmetic can't overflow for any `i32` input.
5. EXIF orientations 3, 6 and 8 have pixel-placement tests.
6. Every PR runs tests, clippy and the frontend build in CI.

## Plan B — Translucent recovery (spec)

Recover real pixels under semi-transparent white or black watermarks by reverse alpha blending. Ship only if it beats the current Telea fill on a ground-truth benchmark. That means no row worse by more than 0.5 dB, at least +2 dB on textured images, and no visible outline (ghost metric ≤ 2.0 plus a human visual check). Otherwise, write a no-go report and do Plan D.

## Plan C — AI upscaling (spec)

- ×2/×4/×8 on an original image or a removal result, fully offline.
- **Models:** Real-ESRGAN (BSD-3), exported to ONNX by us from the official weights. The Fast model (4.9 MB) is bundled; the Quality model (67 MB) downloads once and is SHA-256 verified.
- **Constraints:**
  - Progress and cancel.
  - A 256 MP output limit.
  - Alpha preserved.
  - Same format and ICC rules as removal.
  - Intel Macs get a Lanczos fallback, because ONNX Runtime has no x86_64-macOS build.

## Plan D — LaMa inpainting (outline, only if B is no-go)

- `Engine::Lama` on the Plan C ONNX runtime, with `Carve/LaMa-ONNX lama_fp32.onnx` (Apache-2.0, 208 MB, fixed 512×512).
- It's a download model with a pinned SHA-256, using Plan C's registry.
- The pipeline crops a square around the hole of side `max(512, 2 × hole)`, resizes it to 512, runs the model, resizes back and composites. That's the existing crop/composite path.
- **Gate:** it must beat Telea on the Plan B benchmark and look clean on your Gemini sample.
